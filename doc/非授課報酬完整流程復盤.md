# 非授課報酬完整流程復盤

日期：2026-07-25

## 背景

協會有講師同時兼任行政工作，需要另外支付非授課報酬並由本人簽領。原系統只有講師鐘點結算與領據，沒有非授課報酬流程。

需求的核心不是單純多做一份 PDF，而是讓非授課報酬完整沿用既有領據的高風險作業控制：

```text
試算預覽
→ 確認寫入結算
→ 結算資料回看
→ 產生領據
→ 查看 PDF
→ Email／LINE 分通道寄送
→ 簽領與付款追蹤
```

## 第一次錯誤

第一次實作將「不要弄得太複雜」錯誤理解為可以縮減流程，做成：

```text
填寫資料
→ 瀏覽器確認
→ 直接寫入
→ 立即產生 PDF
```

因此缺少：

- 後端正式試算預覽。
- 試算與寫入分離。
- 寫入結算與產生 PDF 分離。
- 結算後回看。
- Email 與 LINE 分通道選擇及回寫。
- 單據總覽、作廢、補發、重新產生的完整相容。
- 端到端營運流程驗收。

此外，第一次部署只更新 GAS，漏掉 GitHub Pages 前端發布；試算表分頁與領據範本又採延遲建立，造成正式畫面、試算表與 Drive 都看不到預期成果。

## 根本原因

### 1. 把介面簡化誤認為流程簡化

「操作單純」代表：

- 欄位少。
- 按鈕清楚。
- 沿用既有版型。
- 不增加不必要的角色或複雜模組。

不代表可以移除：

- 預覽。
- 二次確認。
- 寫入防呆。
- 單據產生資格。
- 寄送資格。
- 狀態回寫與稽核紀錄。

### 2. 只重用程式碼，沒有重用業務狀態機

沿用既有功能時，不能只看 PDF 產生函式或表單外觀；必須先列出原流程的所有狀態、動作、資格與副作用。

### 3. 把技術成功當成功能完成

下列結果只能證明程式可發布，不能證明功能完成：

- TypeScript 編譯成功。
- GAS push 成功。
- Web App 部署成功。
- GitHub push 成功。

功能完成還必須驗證正式使用者能依正確順序操作，而且每個階段的資料與狀態正確。

### 4. 發布面沒有完整列舉

本專案至少有三個不同發布面：

1. GAS 後端程式。
2. GAS Web App 正式部署版本。
3. GitHub Pages 的 LIFF 前端。

只更新其中一個，不代表整體功能已上線。

## 正確修正

### 資料狀態

`非授課報酬表` 分開保存：

- 結算狀態。
- 領據 PDF。
- Email 狀態。
- LINE 狀態。
- 簽領狀態。
- 付款狀態。
- 來源鍵值。
- 建立時間。
- 操作人。

Email 與 LINE 不得合併為單一寄送狀態。

### 正確流程

#### 試算預覽

- 由後端重新計算應付、扣繳、補充保費及實付。
- 不寫入試算表。
- 不配置正式單號。
- 不產生 PDF。
- 不建立單據紀錄。

#### 確認寫入結算

- 必須帶入試算產生的來源鍵值。
- 使用鎖定避免同時操作產生重複單號。
- 配置 `W_YYYY_MM_###`。
- 寫入結算資料。
- 不產生 PDF。
- 不寄送通知。

#### 產生領據

只有符合以下條件才可勾選：

- 已結算。
- 有正式領據編號。
- 金額完整。
- 尚未產生 PDF。

確認後才產生 PDF 並寫入 `單據紀錄表`。

#### 寄送通知

- 已有 PDF 才能寄送。
- Email 與 LINE 分別顯示是否可用。
- 每個通道分別勾選、執行及回寫。
- 缺 Email 不影響 LINE。
- 缺 LINE ID 不影響 Email。
- 一般寄送不得重複寄送已完成的通道。
- 補發必須改走單據工具。

#### 單據管理

`非授課報酬領據` 必須支援：

- 單據總覽。
- 作廢。
- 補發。
- 尚未對外寄送前重新產生。

## 正式驗收證據

本次修正版完成後執行：

- TypeScript/GAS 建置。
- 前端內嵌 JavaScript 語法檢查。
- 正式 GAS 試算 API 驗證。
- 確認正式試算沒有寫入測試資料。
- 既有資料欄位遷移檢查。
- GitHub Pages 六個操作入口檢查：
  - 試算預覽。
  - 確認寫入結算。
  - 產生領據。
  - 寄送通知。
  - 標記已簽。
  - 標記已付款。
- 單據總覽、作廢、補發、重新產生預覽相容檢查。

正式發布版本：

- GAS Web App：版本 98。
- Git 提交：`ceb3a45`。

## 後續通用規則

當需求出現「沿用」、「套用既有流程」、「照原本模式」時，開始寫程式前必須先完成以下對照：

| 檢查面向 | 必問內容 |
|---|---|
| 狀態 | 原流程有哪些待處理、完成、失敗、作廢狀態？ |
| 動作 | 預覽、寫入、產生、寄送是否為不同動作？ |
| 資格 | 每個按鈕在什麼條件下才可勾選？ |
| 副作用 | 哪一步會寫表、產生 PDF、寄 Email、推 LINE？ |
| 防重複 | 如何避免重複寫入、重複單號、重複寄送？ |
| 回看 | 完成後如何查詢及查看 PDF？ |
| 補救 | 是否支援作廢、補發、重新產生？ |
| 權限 | 前端與後端是否都重新檢查？ |
| 發布 | GAS 程式、Web App 版本、GitHub Pages 是否全部更新？ |
| 驗收 | 是否在正式環境逐階段驗證，而不是只看編譯成功？ |

## 核心結論

> 簡化的是操作表面，不是帳務控制；沿用的是完整狀態機，不只是畫面或 PDF 函式。

這次案例應作為未來新增任何寫入、結算、單據、Email 或 LINE push 功能的標準範例。
